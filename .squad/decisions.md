# Issue #74 — Community STFC sheet ingestion: scope and structure decision

**By:** Picard (M2/EM)
**Date:** 2026-05-31
**Issue:** https://github.com/Jamula/stfc/issues/74
**PR:** https://github.com/Jamula/stfc/pull/75
**Status:** Active (shipped, awaiting merge)
**Requested by:** cyrusj

## What

Mirror the community Google Sheet *Starfleet Academy, Athena & Duo Waves — M90 & M91* (by JulesVern, Quasel, BlueMandalorian, and the STFC Officer Tool Discord `#data-collection` channel) into our repo as agent-readable markdown.

## Scope decision

Game-strategy data is **not consumed by our CLI at runtime**. The value of mirroring is twofold:

1. Context for STFC-domain agents (notably Uhura) reasoning about features.
2. Stable, greppable reference for the project owner.

Therefore the mirror lives under `docs/stfc-knowledge/community-reference-sheet/` — a docs-time artifact, **not** a runtime data path under `data/` and **not** a schema-validated input. CSVs are preserved raw (percent signs, thousand separators) so downstream consumers normalize as they prefer rather than us picking a normalisation everyone has to live with.

## Doc structure

```
docs/stfc-knowledge/
└── community-reference-sheet/
    ├── README.md                       # index, attribution, refresh procedure, limitations
    ├── 01-intro.md                     # one file per tab (gid)
    ├── 02-sf-academy-building.md
    ├── 03-refinery.md
    ├── 04-athena.md
    ├── 05-duo-wave-defense.md
    ├── 06-system-map.md
    ├── 07-credit-calculator.md
    ├── 08-crews-academy-drones.md      # "Blue's Crews" upstream
    ├── 09-independent-archives-m91.md
    ├── 10-g5-scrapping-guide.md
    └── 11-critical-damage-mitigation.md
scripts/
└── fetch-community-sheet.mjs           # re-fetch helper (script generates the headers)
```

Each per-tab file: standard attribution header (source URL with `#gid=`, authors, Discord invite, last-fetched date, "read-only mirror" notice) followed by a fenced ` ```csv ` block with empty columns trimmed.

Cross-links from `README.md` (project layout) and `docs/stfc-game-knowledge.md` §14 so the mirror is discoverable from existing entry points.

## Attribution pattern (now codified)

Because the per-tab header is **generated by `scripts/fetch-community-sheet.mjs`'s `header()` function**, refreshing the mirror cannot accidentally drop attribution. Refreshes only update the "Last fetched" date and the CSV body; the attribution block is rewritten from constants every run.

## Sheet-fetch technique (now codified in skill)

1. Fetch the `/htmlview` URL — its source contains a JS `items.push({name, gid})` array that maps every tab name to its gid. The `/edit` page does **not** expose this.
2. For each gid, fetch CSV via `https://docs.google.com/spreadsheets/d/<SHEET>/gviz/tq?tqx=out:csv&gid=<GID>`.
3. Trim empty columns before writing (upstream uses heavy merged-cell layout, so raw CSVs are ~50% empty columns).

See `.squad/skills/mirror-google-sheet/SKILL.md` for the reusable pattern.

## Tabs noted in issue but missing upstream

*Facade Expansion* and *Emerald Chain Expansion* are not present in the upstream sheet as of 2026-05-31. The index README documents how to add them back to `TABS` in the fetcher if they reappear.

- **No hand-off to Uhura or Tuvok.** Scope was bounded (11 tabs, one fetcher, one index); no STFC-domain disambiguation required (we preserve authors' terminology verbatim); no editorial polish needed beyond the plainly factual index README. Adding hand-offs would have added latency without quality.
- **No sub-issue filed.** The mirror is self-contained. The only natural follow-up is "schedule periodic refresh via CI," which is a Cyrus decision (CI minutes vs. staleness tolerance), not a Picard one.
- **No constitution / plan-template changes.** Docs-only PR; constitution clauses on durable inputs / sanctioned outbound destinations don't apply (the fetch is a developer-machine operation, not a runtime workflow).
- **No pinning-test debt.** No workflow YAML touched (Rule 3 N/A).

### 2026-05-31T19:35:09Z: User directive — track lineage on all ingested knowledge
**By:** cyrusj (via Copilot)
**What:** Whenever the team ingests knowledge from any external source (Google Sheets, Discord channels, web pages, community wikis, screenshots, etc.) into our knowledge base or docs, the lineage MUST be tracked on every ingested artifact. - **Captured / mirrored on** (ISO 8601 UTC date)
- **License or attribution requirements** if any

This applies retroactively to in-flight work (#74) and to all future ingestion (#74's follow-up: STFC Discord channel 1115978499400933473).

**Why:** User request — captured for team memory. Provenance is non-negotiable for community-sourced content.

## What

Research on data sources for seeding ~35–40 officer records for the crew optimizer's initial officer database. The optimizer needs name, captain maneuver text, officer ability text, BDA role, faction enum, and rank curves for each officer across six synergy groups.

## Research summary

Four options evaluated:

1. **Option A: Hand-curate from `docs/stfc-game-knowledge.md`** (RECOMMENDED)
   - 25 officers explicitly named in Section 6 tables; extend with ~10–15 community-known fringe officers (Tomalak, Gowron, Chang, Tom Paris, Seven of Eleven, Charvanek, Sela, etc.)
   - Effort: 1–2 days to author ~35–40 officers
   - Maintenance: ongoing per STFC patch (~monthly); loud unknown-officer error path per plan
   - Licensing: zero risk (hand-authored from functional facts, no creative expression or IP)
   - Coverage: all six synergy groups needed for v1

2. **Option B: Scrape stfc.space** (BLOCKED — HIGH RISK)
   - Site is closed-source Vue.js SPA; no public API
   - TOS completely invisible; estimated 180–200 officers
   - Licensing risk: HIGH. Scopely IP + database compilation rights unclear

3. **Option C: Official STFC database** (BLOCKED — UNUSABLE)
   - Account login wall; no public export or API
   - Scopely TOS prohibits scraping

4. **Option D: Community sources** (REFERENCE ONLY)
   - `mjstelly/stfcofficertool` CSV: use as completeness checklist only (no ability text, no synergy groups, unlicensed)
   - STFC Fandom Wiki: CC BY-SA; use for manual reference during hand-authoring, not bulk copy
   - STFC Officer Tool Discord `#data-collection`: best future path for v1.x licensed snapshot

## Recommendation

**For v1: Use Option A** — hand-curate ~35–40 officers from existing game knowledge + community fringe officers. Zero licensing risk, covers all synergy groups, timeline fits v1 delivery.

**For v1.x: Outreach to STFC Officer Tool Discord** (#data-collection channel) to request CC-licensed officer-abilities snapshot; adapt the existing `scripts/fetch-community-sheet.mjs` pattern for refresh.

**Do NOT pick Options B or C** — blocked and high-risk.

## Roster privacy default — TRACKED-BY-DEFAULT

`data/crew/roster/*.yaml` is committed by default. Operators who want
private rosters opt out via a one-line `.gitignore` snippet
documented in `docs/CREW-OPTIMIZER.md` § 6.

**Why:** keeps the optimizer reproducible across operator machines;
lets the CI workflow regenerate `docs/crew/{account}.md` reliably;
trivial opt-out for privacy-conscious operators; missing roster
files are not an error (skip with warning, exit 0 for other
accounts). The alternative (gitignore-by-default with explicit
opt-in) would create surprising empty per-account reports in CI for
first-time operators and force a "first-run helper" into
`skill:roster`.

Encoded in FR-004, plan §Constitution Check (Principle V), research
R4, data-model invariants, roster.contract.md, quickstart §6, and
constitution v1.6.0 Principle V.
